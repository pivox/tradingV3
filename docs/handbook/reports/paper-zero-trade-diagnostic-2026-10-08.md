# Paper zero-trade diagnostic — Hyperliquid day trading long (2026-10-08)

## Result and scope

One full, baseline-eligible Hyperliquid replay of `day_trading@1.1.0 / day_trading.trend_continuation.long@1.1.0 / long` consumed all **1,488,002** frozen events and produced **zero accepted decisions, intents, orders, fills or certified trades**. The journal's first demonstrated trade-path break is plan construction: **191** observations have `missing_evidence/paper_order_plan_unavailable`; **one** further observation has `no_trade/paper_canonical_strategy_setup_section_failed`. A targeted, read-only reconstruction of a genuine plan-unavailable trigger proves that its underlying rejection is `canonical_entry_zone_candidate_outside`: the bid is **86,294** versus a computed entry zone **[84,918, 85,004]**. The journal does not retain the underlying reason for the other 190 plan-unavailable observations, so their precise causes remain unproven.

This is a diagnosis of one cell on one dataset. It does not justify changing immutable `1.1.0` contracts or engine behavior.

## Counts and first broken boundary

The [diagnostic query](queries/paper-zero-trade-diagnostic.sql) runs read-only on the disposable database and fails if the run has zero or multiple cells. It counts both explicit `strategy_observed` rows (`weight=1`) and `replay_batch.payload.observations` triplets (`[status, reason_code, count]`, weighted by `count`). It keeps `[null,null,count]` separate from missing evidence. This run has **298 `replay_batch` rows + 298 `fake_state_snapshot` rows = 596 journal rows**, representing **1,488,002** source events; it has no explicit `strategy_observed` rows and no null/null triplets. Counting 596 rows as 596 observations would be wrong.

| Observation or artifact | Exact count |
| --- | ---: |
| `missing_evidence / paper_indicator_projection_unavailable` | 1,487,810 source events |
| `missing_evidence / paper_order_plan_unavailable` | 191 source events |
| `no_trade / paper_canonical_strategy_setup_section_failed` | 1 source event |
| `order_intent`, `trade_lineage`, `trade_lifecycle_event`, `fill_cost_ledger`, `trade_zone_events`, `position_trade_analysis_v2` | 0 rows each |
| Certified trade export | 0 data rows; header only |

The raw dataset contains **692** confirmed `candle_15m` events: **500** historical `rest_candle_snapshot` and **192** live-window `ws_candle`. The published setup's execution timeframe is 15m ([contract](https://github.com/pivox/tradingV3/blob/88c500a02f7d86ce6dd7d11e7343048ac4554ae2/trading-app/config/trading/setup_contract/day_trading.trend_continuation.long/1.1.0.yaml)), and [the evidence provider](https://github.com/pivox/tradingV3/blob/88c500a02f7d86ce6dd7d11e7343048ac4554ae2/trading-app/src/Trading/Paper/Execution/Strategy/PaperCanonicalStrategyEvidenceProvider.php) rejects other channels and unconfirmed candles before computing projection. Thus the millions of `paper_indicator_projection_unavailable` observations do **not** by themselves prove a warmup defect. Some trigger-shaped historical candles can also lack enough indicator history; the compressed journal does not link each such observation back to its raw channel. The **192** observations that reached a plan result or setup rule equal the live-window 15m candle count, but this equality alone is not an event-by-event lineage proof.

The actual boundary is: trigger and indicator/book/instrument/cost evidence can reach [plan construction](https://github.com/pivox/tradingV3/blob/88c500a02f7d86ce6dd7d11e7343048ac4554ae2/trading-app/src/Trading/Paper/Execution/Strategy/PaperCanonicalStrategyEvidenceSource.php); `build()` returns `null`, which is turned into `paper_order_plan_unavailable`; [preparation](https://github.com/pivox/tradingV3/blob/88c500a02f7d86ce6dd7d11e7343048ac4554ae2/trading-app/src/Trading/Paper/Execution/Strategy/PaperCanonicalStrategyPreparation.php) records `missing_evidence` and no decision. The other one case passes plan construction but fails a setup rule. With no canonical decision, [the coordinator](https://github.com/pivox/tradingV3/blob/88c500a02f7d86ce6dd7d11e7343048ac4554ae2/trading-app/src/Trading/Paper/Execution/PaperExecutionCoordinator.php) does not reserve an order intent or append a `trade_entry` effect. Therefore order, fill, close, cost and lineage stages have no rows. The [certified export](queries/bad-trades-baseline-v2.sql) being empty is consistent with this chain, but would not establish it on its own.

## Underlying reason proven on one real trigger

The private targeted probe read the same verified dataset in the replay's sorted `candleAvailability(CANDLE_15M)` order and reconstructed the same snapshot, config and cell hashes. At sorted source position **8180** (event ID `091787e65357234bf4fdfbc8bb372232587e5da4cda59f1fe197a8698ebbecb4`), it observed the underlying exception `canonical_entry_zone_candidate_outside` before the [plan evidence source](https://github.com/pivox/tradingV3/blob/88c500a02f7d86ce6dd7d11e7343048ac4554ae2/trading-app/src/Trading/Paper/Execution/Strategy/PaperCanonicalOrderPlanEvidenceSource.php) converted one of six expected plan exceptions to `null`. The [entry-zone engine](https://github.com/pivox/tradingV3/blob/88c500a02f7d86ce6dd7d11e7343048ac4554ae2/trading-app/src/TradingCore/OrderPlan/Canonical/CanonicalEntryZoneEngine.php) is the throw site.

Observed inputs at 8180: long best bid **86,294**, best ask **86,295**, 5m VWAP anchor **84,961.48015813975**, 5m ATR **126.46730411017666**, tick **1**, equity **100,000**. Contract parameters are ATR multiplier **0.30**, minimum half-width rate **0.0005**, maximum **0.0100**, zero asymmetry. Using the production BigDecimal formula, the minimum half-width **42.480740079069875** dominates ATR × 0.30; floor/ceiling tick rounding yields **[84,918, 85,004]**. The bid is **1,290** above the upper bound. The zone object is not persisted because the engine throws before creating it; these bounds are a calculation from the observed inputs, not a captured order plan.

The one probe execution also printed later samples, but its state handling for those samples was found to differ potentially from baseline. Its archived script was corrected afterward and passed `php -l`, but **was not rerun**. Only position 8180 supports the exact underlying-reason conclusion. The journal's generic `paper_order_plan_unavailable` does not prove that all 191 positions failed for the same reason.

## Minimal next lot

Preserve this database and private evidence while reviewing. Add a narrow, redacted diagnostic at the expected-exception catch in `PaperCanonicalOrderPlanEvidenceSource::build()` to retain the six possible reason codes and the zone inputs/bounds for genuine execution triggers, without changing decisions or immutable `1.1.0` contracts. Validate the diagnostic on a small, isolated trigger replay, then use those reason counts to decide whether a new versioned setup needs calibration. No full 12-cell campaign or parameter tuning is supported by this report alone.
